# 문서 형식과 단계 완료 기준

경로는 작업별 문서 루트 기준이다. 사용자의 기존 구조가 있으면 대응 경로를 `00-progress.md`에 적는다. 아래는 작성할 항목이지 완성된 문서가 아니다. 조사하지 않은 내용을 예시 값으로 채우지 않는다.

## 00-progress.md — 진행 인덱스

목표, 실행 모드, 대상 프로젝트, 문서 루트, 포함·제외 범위, 구현 담당과 실제 모델 설정을 기록한다. 지정되지 않은 모델은 미지정으로 적는다.

```markdown
## 단계
| 단계 | 상태 | 산출물 | 완료 조건 | 남은 작업 |
| --- | --- | --- | --- | --- |

## 태스크 상태
| ID | 상태 | 선행 태스크 | 담당 | 명세 | 결과 | 차단 사유 |
| --- | --- | --- | --- | --- | --- | --- |

## 이어서 할 작업
- 현재 위치:
- 바로 다음 행동:
- 필요한 정보:
- 마지막 갱신 시점:
```

단계와 태스크 상태의 기준은 이 문서다. 다른 인덱스에서 상태를 중복 관리하지 않는다. 상태를 바꾸면서 실제 산출물 링크와 필요한 작업을 함께 갱신한다.

## 01-discovery.md — 현황 분석

- 현재 코드와 원본·참고 자료의 위치, 접근 가능 여부
- 목표와 관련된 기술 스택, 주요 파일, 의존성, 실행·검증 명령
- 기존 동작, 재사용 가능 부분, 예상 통합 충돌
- 확인한 사실의 코드·자료 근거
- 가정과 확인 필요 사항, 누락 자료의 영향

**완료 기준:** 설계에 필요한 구조와 근거가 있다. 핵심 자료가 없으면 확인 가능한 부분만 기록하고 영향받는 후속 작업을 차단한다.

## 02-requirements.md — 요구사항

요구사항에 R01, R02처럼 작업 내 고유 ID를 부여한다.

| ID | 사용자 행동 또는 트리거 | 기대 결과 | 수용 기준 | 근거 / 미확정 사항 |
| --- | --- | --- | --- | --- |

포함·제외 범위, 유지할 기존 동작, 필요한 질문을 적는다. 질문에는 영향을 받는 요구사항 ID를 연결한다.

**완료 기준:** 구현 범위와 관찰 가능한 수용 기준이 명확하다. 핵심 미확정 요구사항은 보류 상태로 남기고, 확정된 범위는 후속 단계로 진행한다.

## 03-architecture.md — 설계

- 현재 구조와 변경 후 구조
- 재사용·이식·신규 구현 구분과 파일 배치
- 주요 경계, 진입점, 데이터·제어 흐름
- 해당하는 상태·예외·복구 시나리오
- 기존 시스템과의 충돌 해결, 변경 영향
- 채택한 구현 선택과 짧은 근거

UI 변경은 라우팅·스타일·화면 상태, 데이터 변경은 저장·정합성·실패 처리처럼 실제 범위에 필요한 항목만 정의한다. 작은 변경은 간결하게 설명한다.

**완료 기준:** 구현 가능한 범위의 구조, 책임, 예외 처리 방식이 정해져 있다.

## 04-contracts.md — 공통 데이터와 인터페이스

- 이름, 책임, 정의할 코드 파일
- 프로젝트 언어에 맞는 타입·스키마·시그니처
- 필수 여부, 기본값, null 허용 여부와 입력 검증
- 반환값, 상태 변경 및 부수 효과
- API가 있다면 메서드·경로·요청·응답·오류 형식
- 정상·경계·오류 예시

기존 계약을 재사용하면 위치와 적용 항목을 링크한다. 새 공유 계약이 없는 작업은 그 사실을 기록한다. 모델·예시는 구현 언어와 확정된 동작에 일치해야 한다.

**완료 기준:** 태스크 사이에서 공유할 계약이 확정된다. 미확정 계약에 의존하는 태스크는 시작하지 않는다.

## 05-task-index.md — 작업 분해

| ID | 태스크 | 요구사항 ID | 선행 태스크 | 수정 파일 | 명세 |
| --- | --- | --- | --- | --- | --- |

태스크는 컴포넌트·함수·클래스 등 명확한 책임 단위로 정의하되, 강하게 결합된 작은 변경은 묶는다. 공통 계약·코드가 먼저 준비되도록 순서를 정한다. 병렬 가능 여부는 파일 범위와 의존성으로 판단한다.

각 `tasks/Txx-spec.md`에 다음을 포함한다.

```markdown
# Txx — 태스크명

- 목적 / 요구사항 ID:
- 선행 태스크 / 시작 조건:
- 참고할 기존 파일:
- 생성·수정할 파일:
- 수정 금지 범위:
- 구현 단위와 공개 인터페이스:
- 관련 계약 문서와 읽을 항목:

## 세부 구현 조건
- 사용할 기존 라이브러리와 공통 코드:
- 처리 순서와 동작 규칙:
- 상태 변경과 부수 효과:
- 입력 검증과 경계 조건:
- 오류 처리와 사용자에게 보여줄 결과:

## 사례
- 정상 입력 또는 행동 → 기대 결과:
- 경계 입력 또는 행동 → 기대 결과:
- 오류 입력 또는 행동 → 기대 결과:

## 검증과 완료 기준
- 필요한 검증 및 실제로 확인한 실행 명령:
- 관찰 가능한 완료 조건:
- 미확정 사항과 차단 조건:

## 구현 에이전트 전달 정보
- 프로젝트 및 적용 지침 경로:
- 필요한 명세·계약·코드·선행 결과 경로:
- 결과 문서 경로:
```

UI 사례는 props, 사용자 행동, 화면 상태로 표현할 수 있다. 불필요한 사례를 만들지 말고 해당하지 않는 조건은 이유를 적는다. 전달 정보는 이전 대화 없이도 필요한 파일을 읽어 작업할 수 있어야 한다.

**완료 기준:** 준비됨인 태스크에 파일 범위·계약·선행 조건·사례·검증·완료 기준이 모두 있다.

## 06-validation-plan.md — 검증 계획

| 검증 ID | 요구사항 / 태스크 | 방법 또는 명령 | 기대 결과 | 필요한 환경 |
| --- | --- | --- | --- | --- |

관련 프로젝트 필수 검사, 변경에 필요한 테스트·빌드·화면 확인, 핵심 사용자 흐름, 영향받는 기존 동작의 회귀 검증을 정의한다. 실제 동작과 실패 처리를 검증하고, 구현을 그대로 반복하는 테스트를 만들지 않는다. 전체 완료 판정 조건을 적는다.

**완료 기준:** 변경 성공 여부를 실제로 판정할 수 있다. 계획 수립 모드라면 여기까지 정리하고 `08-final-report.md`에 계획 완료와 미구현 범위를 기록한다. 구현·통합 검토 단계는 미시작으로 유지한다.

## results/Txx-result.md — 태스크 결과

구현 시작 시 생성하고 구현·수정·검증 결과로 갱신한다.

```markdown
# Txx — 구현 결과

- 구현 보고: 검토 요청 / 부분 완료 / 차단
- 실제 담당 및 실행 설정:
- 생성·수정한 파일:
- 핵심 변경:
- 완료 기준별 충족 여부:

## 검증
| 방법 또는 실제 명령 | 기대 결과 | 실제 결과 | 실행 여부 |
| --- | --- | --- | --- |

## 남은 사항
- 미충족 기준:
- 미실행 검증과 이유:
- 필요한 정보 / 선행 작업:
- 후속 태스크에 미치는 영향:

## 상위 검토
- 검토한 변경과 근거:
- 보완 요청 / 재검증 결과:
- 최종 판정:
```

‘구현 보고’는 담당자의 보고이지 태스크 상태의 기준이 아니다. 검토 후 최종 상태를 `00-progress.md`에 반영한다.

## 07-integration-review.md — 통합 검토

- 요구사항별 수용 기준과 충족 근거
- 태스크 간 계약·연결·실패 처리의 일관성
- 계획된 필수 검사와 핵심 흐름의 실제 결과
- 기존 동작 회귀 검증 결과
- 발견한 결함, 영향, 보완 태스크, 재검증 결과
- 미실행 검증과 미해결 사항

결함은 관련 태스크를 다시 열거나 보완 태스크로 정의하고 명세·결과·인덱스를 갱신한다. 필수 검증을 실행하지 못했으면 통합 검토 완료로 표시하지 않는다.

## 08-final-report.md — 최종 보고

실행 모드, 현재 범위의 상태, 전체 목표의 상태를 구분한다. 상태는 완료 / 부분 완료 / 차단으로 표시한다.

- 완료한 계획 또는 구현 범위
- 주요 문서·변경 파일 링크
- 실행 방법과 검증 결과
- 남은 미확정 사항·결함·미실행 검증
- 다음 행동

계획 작성 완료를 구현 완료로 취급하지 않는다. 전체 목표는 요청한 동작과 필수 검증을 충족한 경우에만 완료로 표시한다.

## decisions.md — 결정 기록

실제 결정이 생겼을 때 D01 같은 ID와 변경 내용, 이유, 영향받는 요구사항·계약·태스크·문서를 기록한다. 중요한 계약 변경은 문서 갱신과 담당자 전달까지 연결한다. 초기에는 ‘기록 없음’으로 두어도 된다.
