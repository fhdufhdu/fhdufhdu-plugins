# 문서 기반 개발 오케스트레이션

사용자의 소프트웨어 변경 목표를 분석 → 요구사항 → 설계·계약 → 태스크 → 검증 계획 → 구현 → 통합 검토 → 최종 보고로 진행한다. 각 단계의 결과와 현재 위치를 프로젝트 문서에 저장해 다른 세션에서도 이어갈 수 있게 한다. 특정 제품, 언어, 프레임워크, 호스팅 서비스에 종속되지 않는다.

## 실행 범위를 먼저 결정한다

- **계획 수립**: 설계·명세·검증 계획까지 문서로 작성한다. 구현 코드는 수정하지 않는다.
- **전체 진행**: 문서 작성 후 구현, 검토, 통합 검증까지 수행한다.
- **이어 진행**: 기존 문서와 실제 코드를 대조하고 남은 허용 작업을 수행한다.

사용자가 지정한 모드를 따른다. 구현을 요청했다면 전체 진행, 계획만 요청했다면 계획 수립이다. 범위가 불명확하면 우선 계획을 작성하면서 실행 범위를 확인한다. 기존 모드가 계획 수립이었다면 재개 요청만으로 구현 허가가 생겼다고 해석하지 않는다.

이미 허용된 단계는 반복 승인을 요구하지 않는다. 스킬 사용은 배포, 병합, 원격 push, 데이터 삭제, 외부 메시지 전송을 추가로 허가하지 않는다. 이런 작업의 범위는 사용자의 실제 요청으로 판단한다.

## 입력과 작업 위치

대화와 저장소에서 목표, 프로젝트 경로, 대상·원본 코드, 포함·제외 범위, 기존 동작, 제약, 실행 모드를 파악한다. 제품 동작이나 공개 계약을 결정할 수 없는 정보만 모아서 질문하고 독립 작업은 계속한다. 확인한 사실과 가정, 미확정 사항을 구분한다.

대상 프로젝트 지침과 관련 코드·의존성·실행 명령을 먼저 읽는다. 기존 구조와 공통 코드를 활용하고, 실제로 확인하지 않은 API·파일·명령을 확정하지 않는다.

문서는 사용자가 지정한 경로 또는 기존 문서 관례를 따른다. 별도 관례가 없으면 `docs/workflows/<작업-slug>/`를 사용한다. 같은 프로젝트의 다른 작업과 문서가 섞이지 않도록 기존 인덱스와 목표를 확인한다. 스킬 설치 폴더에는 프로젝트 기록을 저장하지 않는다.

## 문서와 계획

계획을 작성하거나 갱신할 때 [문서 형식과 완료 기준](references/documents.md)을 읽는다. 기존 계획을 재개하면 먼저 진행 인덱스와 해당 태스크·결과·코드를 읽고, 필요한 형식만 확인한다.

| 단계 | 기준 문서 |
| --- | --- |
| 진행 관리 | `00-progress.md` |
| 현황 분석 | `01-discovery.md` |
| 요구사항 | `02-requirements.md` |
| 아키텍처 및 공통 계약 | `03-architecture.md`, `04-contracts.md` |
| 태스크 명세 | `05-task-index.md`, `tasks/Txx-spec.md` |
| 검증 계획 | `06-validation-plan.md` |
| 태스크 구현 결과 | `results/Txx-result.md` |
| 통합 검토 | `07-integration-review.md` |
| 최종 보고 | `08-final-report.md` |
| 주요 결정과 변경 영향 | `decisions.md` |

초기 공통 문서를 만들되 미진행 단계는 ‘미시작’으로 명시한다. 태스크 명세는 작업을 정의할 때, 결과 문서는 구현을 시작할 때 생성한다. 문서 양은 변경 규모에 맞춘다. 해당하지 않는 항목은 이유를 적고 제외하며, 문서를 채우려고 인증·API·아키텍처를 추가하지 않는다.

요구사항 → 태스크 → 검증의 연결을 유지한다. 공유 계약을 먼저 확정하고, 계약이 미확정인 태스크는 준비됨으로 표시하지 않는다. 같은 파일을 수정하는 태스크는 기본적으로 순차 실행한다.

## 구현과 위임

구현을 시작할 때만 [구현 에이전트 지침과 검토 절차](references/implementation.md)를 읽는다. Sol은 현재 세션의 설계·진행 관리 역할, Luna는 하위 구현 역할을 뜻한다.

하위 에이전트 기능이 있으면 명확한 책임과 파일 범위로 위임한다. 별도 사용자 채팅을 생성하지 않는다. 요청되지 않은 모델 선택은 현재 실행 환경의 기본값을 따르며, **서브에이전트의 reasoning effort 기본값은 `medium`**으로 설정한다. 태스크 난이도와 불확실성에 따라 effort를 적절히 낮추거나 높인다. 사용자가 명시적으로 지정한 모델·추론 수준은 우선 적용한다.

effort는 역할명이 아니라 실행 도구에서 설정하고, 해당 모델·도구가 지원하는 값만 사용한다. 선택 기준은 [구현 에이전트 지침](references/implementation.md)의 ‘추론 수준 선택’을 따른다. 태스크 명세에 선택한 수준과 이유를 적고, 결과 문서에는 실제 설정과 변경 이유를 남긴다.

에이전트나 지정 설정을 사용할 수 없으면 제약을 기록한다. 특정 모델 사용이 필수라면 해당 위임을 차단하고 독립 작업을 계속한다. 모델이 선호 사항이거나 위임 기능만 없는 경우에는 현재 에이전트가 같은 명세와 검증 기준으로 작업할 수 있다. 설정한 적 없는 모델을 사용했다고 보고하지 않는다.

구현 에이전트는 지정 코드와 자기 결과 문서만 수정한다. 진행 인덱스와 공통 계약은 Sol이 관리한다. 태스크는 구현 보고만으로 완료하지 않고, 실제 변경·완료 기준·검증 근거를 검토한 뒤 완료 처리한다.

## 진행 관리와 재개

- `00-progress.md`를 상태의 기준으로 삼고 단계 시작·완료·차단 및 태스크 상태 변화 시 갱신한다.
- 단계 상태: 미시작 / 진행 중 / 완료 / 차단.
- 태스크 상태: 계획 / 준비됨 / 진행 중 / 검토 대기 / 완료 / 차단.
- 설계·계약 변경은 `decisions.md`에 이유와 영향받는 문서·태스크를 기록하고 관련 명세를 갱신한다.
- 차단된 태스크 때문에 독립 작업을 멈추지 않는다. 중단 시 차단 사유와 바로 다음 행동을 적는다.
- 재개 시 문서의 완료 표시, 실제 변경, 선행 작업, 검증 결과가 일치하는지 확인한다. 오래된 검증은 관련 코드·계약·환경이 바뀌었을 때 다시 수행한다.
- 구현을 끝내지 못했거나 필수 검증이 미실행이면 전체 목표를 완료로 표시하지 않는다.

사용자에게는 현재 단계, 중요한 결정, 다음 작업을 간결하게 알린다. 최종 응답은 실행한 모드, 문서 인덱스 링크, 완료 범위, 검증 결과, 남은 작업으로 정리한다. 파일 저장 도구가 없다면 경로별 문서 내용을 제공하고 ‘미저장’ 및 실제로 수행하지 못한 작업을 명시한다.
